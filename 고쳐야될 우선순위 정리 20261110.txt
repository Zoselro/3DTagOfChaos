내 판단으로는 다음 대규모 기능을 추가하기 전에 이 클래스를 정리하는 게 좋겠어.

단, 기존 이동과 네트워크 동작을 한 번에 옮기면 회귀 버그가 생길 수 있으므로 단계적으로 분리해야 해.

2. EscapeManager와 EscapeAuthority의 역할 (우선순위 높음)

두 클래스의 역할 분리는 기본적으로 잘되어 있어.
클래스	책임
EscapeManager	전체 클라이언트의 상태 동기화, 요청 전달, 화면 갱신, 지형 검사
EscapeAuthority	방장의 게임 규칙 처리, 상태 변경, 요청 검증
EscapeState	게임 상태 데이터 저장 및 직렬화
EscapeRequest	클라이언트가 요청하는 데이터
EscapeGate	탈출구 표현
QuadrantBuilding	사분면 건물 표현

문제는 두 핵심 클래스가 너무 커졌다는 거야.
현재 핵심 클래스 크기
EscapeAuthority - 1,536줄
EscapeManager - 597줄
HideOrSeekPlayer - 741줄
DecoyBrain - 534줄

이번에 직접 가져온 C# 파일의 줄 수. 이전 조사 문서의 수치와 차이가 있어 현재 코드 기준으로 다시 표시했어.
특히 EscapeAuthority가 1,536줄이라는 것은 단순히 길다는 문제가 아니야.

이 클래스가 담당하는 기능이 너무 많다는 게 핵심이야.
- 상자 열기
- 아이템 획득 및 드롭
- 건물 수리
- 건물 해체
- 탈출구 판정
- 로켓 탈출
- 무지개 상자
- 헬리콥터 모자
- 사이렌 함정
- 호박마차
- 콜라 대포
- AI 미끼 잡기
- 위치 검증
- 스태미나 추정
- 재료 복구
즉, 탈출 시스템의 거의 모든 규칙이 한 클래스에 집중되어 있어.

현재 클래스를 무작정 여러 개로 쪼개기보다는 기능별 서비스로 분리하는 것을 추천해.

EscapeAuthority - 요청 분배 및 상태 변경 총괄

InventoryService - 아이템·상자 (분리)
BuildingService - 수리·해체 (분리)
EscapeService - 탈출·로켓 (분리)
ToolService - 도구·폭탄 (분리)
VehicleService - 마차·대포 (분리)
MovementValidator - 거리·이동 검증 (분리)

EscapeState - 단일 게임 상태 데이터

3. EscapeManager 클래스 (우선 순위 높음)

- IsWalkableFromSpawn()
- TryReachAnchor()
- IsValidTeleport()
- SafeGroundPoint()
- FallbackDropPoint()
- SnapToGround()

이 기능들은 게임 규칙보다는 맵과 지형에 관한 책임이야.

따라서 다음 구조를 추천해.

EscapeStateSynchronizer: Room Properties 상태 관리
EscapeRequestGateway: 요청 수신 및 전달
EscapeViewPresenter: 오브젝트 표현 갱신
EscapeGeometry: 맵 지형, 위치, NavMesh 검사

이렇게 하면 새로운 맵을 추가할 때 탈출 규칙을 건드리지 않고 지형 검사만 확장할 수 있어.

4. PunSceneLoad (우선순위 높음)

씬 로드가 취소되면서 Unity의 비동기 로드가 90%에서 멈추는 문제를 해결하기 위해서 추가가 된 클래스 인거같아.
실제 문제를 해결하려는 접근은 좋지만, PUN 내부 구현에 의존한다는 단점이 있어.

내 추천은 이 코드를 삭제하는 게 아니라 독립적인 호환성 계층으로 유지하는 거야.

PUN 업데이트 때 다음 항목을 확인하도록 해야 해.
- Reflection 필드 존재 여부
- 씬 로드 진행 상태
- 취소된 로드 복구 여부
- 방장 변경 중 씬 이동 여부

이는 삭제를 의미하는게 아닌 보강이 목적임.

5. 위치 기록 시스템 중복 (우선순위 매우 높음)

EscapeAuthority.lastPositions	ActorNumber	약 0.2초	거리 및 이동 검사
PositionHistory	PhotonView.ViewID	0.05초	잡기 판정 및 과거 위치

같은 캐릭터 위치를 서로 다른 시스템에서 기록하고 있어.

문제는 ActorNumber는 플레이어를 구분하지만 ViewID는 캐릭터 객체를 구분한다는 점이야.

한 플레이어가 여러 캐릭터를 소유하는 상황에서는 ActorNumber 기반 기록이 섞일 수 있어.

개선안: PositionHistory를 중심으로 통합하고, ActorNumber와 ViewID 사이의 조회 관계를 별도로 제공하는 방식이 좋아.

또 하나, EscapeAuthority.IsNear()는 위치 기록이 없으면 통과시키는 구조야.
if (!lastPositions.TryGetValue(actor, out Vector3 at))
    return true;


입장 직후를 고려한 예외지만, 보안 검증 관점에서는 위치가 확인되지 않은 요청을 허용하는 것이므로 별도 검토가 필요해.

6. Manager 의존성 (우선순위 보통)

현재 EscapeManager.Instance와 정적 속성들을 여러 시스템이 직접 참조하고 있어.

예를 들면:
- Camera
- Audio
- Monster
- Unit
- GameManager

이렇게 되면 EscapeManager의 내부 구현을 변경할 때 영향을 받는 클래스가 많아져.

장기적으로는 EscapeContext 같은 씬 단위 접근 객체를 두고 필요한 기능만 제공하는 방식이 좋아.

단, 지금 당장 전체 Singleton을 제거할 필요는 없어.

7. 4. AI 시스템 (우선순위 낮음)

현재 DecoyNavMesh.Ready가 준비되지 않으면 AI 판단을 진행하지 않아.

따라서 맵의 NavMesh가 누락됐을 때 AI가 멈추는 것은 의도된 동작인지, 사용자에게 경고를 보여줘야 하는지 결정하면 좋겠어.

내 생각에는 이 AI 시스템은 지금 당장 구조를 바꾸지 않는 게 좋을거 같고, 대신

- AI 이동 및 추적 로직은 수정하지 않기
- DecoyNavMesh.Ready의 초기화 흐름 유지
- NavMesh 미준비 상태에서 AI가 대기하는 현재 동작 유지
- 나머지 시스템 리팩터링 중 AI에 영향을 주는 변경이 있는지만 확인하기
